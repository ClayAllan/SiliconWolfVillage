# P2-A 页面刷新与快照锁成本测量（2026-10-30）

## 结论摘要

本轮首次按 app.py 的正常活动对局路径测量了**三次快照组成的一次页面刷新数据链路**，并分别计时快照总耗时、服务锁等待、锁持有、deepcopy、真人行动完整性检查、视角投影和动态窗口选择。

在 15,000 条合成公开事件下：

- 一次页面刷新数据链路中位数 **169.89 ms**，P95 **181.88 ms**。
- 正常活动对局一次 rerun 有 **3 次 GameService.snapshot()**；单次快照中位数 **46.23 ms**。
- 快照锁持有中位数 **46.22 ms**，其中 copy.deepcopy 中位数 **46.13 ms**。快照锁内的耗时几乎全部由深拷贝构成。
- 锁等待中位数只有 **0.001 ms**；在后台 worker 并发时，锁等待 P95 为 **0.300 ms**。当前主要问题不是等待获取锁，而是持锁执行深拷贝的时间。
- project_view() 中位数 **32.20 ms**；动态窗口选择中位数 **0.058 ms**；真人行动完整性检查每次中位数 **0.018 ms**。
- 以 1.5 秒为刷新间隔、每次刷新执行三次快照时，合成 worker 吞吐保持率 **88.9%**。该轮只有 4 次页面刷新、12 次快照，属于诊断性小样本，不是线上吞吐保证。

**判断：下一阶段应优先研究减少重复快照和降低快照深拷贝成本，其次研究视角投影；不应继续把主要精力放在已经降至亚毫秒级的 Feed 窗口选择上。**

## 2. 页面刷新调用链核验

app.py 中 sync_game_state() 的全部调用点：

- 全部调用点：298、356、394、422、433、515、529、541、840、899。
- 模块顶层 rerun 调用点：422、433、515、529、541、840、899。
- 正常活动对局路径：**422 → 515 → 840**，对应 3 次 GameService.snapshot()。

其他调用点是条件路径：

- 433：终局补归档后重新同步。
- 529：用户点击“应用设置”后重新同步。
- 541：用户点击“测试连接”后重新同步。
- 899：真人提交行动后同步，并触发新的 rerun。
- 298、356、394 位于创建新局、开始推进和单步推进等辅助函数中，不属于每次正常页面 rerun 都执行的调用。

基准中的一次正常页面刷新数据路径按以下顺序模拟：

1. GameService.snapshot() → app.py 原始真人行动完整性检查。
2. GameService.configure() → 第二次快照 → 完整性检查。
3. 第三次快照 → 完整性检查。
4. project_view(snapshot.engine, viewer_seat=human_seat)。
5. 初始化实际 Feed 状态并执行 select_feed_window(..., limit=90)。

完整性检查函数直接从 app.py AST 中提取并执行，没有导入或运行 Streamlit。配置阶段使用当前快照中的 react_budget 值。

## 3. 独立页面刷新数据链路

单位：毫秒。Snapshot 的 P50/P95 基于每个页面刷新中的全部快照样本；页面数据链路 P50/P95 基于 9 次刷新样本。

| 公开事件数 | 页面数据链路 P50 / P95 | 单次 Snapshot P50 / P95 | 锁等待 P50 | 锁持有 P50 | deepcopy P50 | 完整性检查单次 P50 | 投影 P50 | Feed 选择 P50 |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 100 | 1.77 / 1.80 | 0.52 / 0.54 | 0.000 | 0.52 | 0.49 | 0.001 | 0.19 | 0.016 |
| 1,000 | 11.14 / 14.67 | 3.19 / 3.26 | 0.000 | 3.18 | 3.15 | 0.002 | 1.54 | 0.021 |
| 5,000 | 52.71 / 57.71 | 14.82 / 18.97 | 0.000 | 14.82 | 14.78 | 0.006 | 7.52 | 0.033 |
| 15,000 | 169.89 / 181.88 | 46.23 / 52.47 | 0.001 | 46.22 | 46.13 | 0.018 | 32.20 | 0.058 |

### 15,000 条事件下的成本解释

- 三次快照合计约 138.7 ms 的中位耗时，是页面数据链路的主要组成。
- 单次 Snapshot 的锁持有约 46.22 ms，其中深拷贝约 46.13 ms。二者差值约 0.09 ms。
- project_view() 仍有约 32.20 ms 的中位成本，主要是遍历公开日志并创建视角数据。
- Feed 窗口选择约 0.058 ms；真人行动完整性检查约 0.018 ms/次。这两项不再是当前主要瓶颈。

这组结果不意味着线上页面必然耗时 169.89 ms。它不包含 Streamlit 组件构建、Markdown/HTML 渲染、WebSocket 传输、浏览器绘制和网络延迟。

## 4. 正常刷新频率下的后台竞争

15,000 条事件；使用真实 GameService worker 和无网络脉冲生成器；比较后台单独推进与每 1.5 秒执行一次完整三快照页面数据路径。

| 指标 | 结果 |
|---|---:|
| Worker 单独推进 | 194.13 步/s |
| 页面刷新期间推进 | 172.49 步/s |
| 吞吐保持率 | 88.9% |
| 页面刷新次数 | 4 |
| Snapshot 次数 | 12 |
| 页面数据链路 P50 / P95 | 177.26 / 179.62 ms |
| Snapshot 锁等待 P50 / P95 | 0.002 / 0.300 ms |
| Snapshot 锁持有 P50 / P95 | 49.36 / 55.41 ms |
| Snapshot deepcopy P50 / P95 | 49.28 / 55.29 ms |

这说明三次快照在正常刷新节奏下也会对后台推进造成可测量影响，但本轮只有 4 个刷新样本。不能将 88.9% 外推为线上固定吞吐，也不能将锁等待与 CPU 竞争混为一谈。

## 5. 快照缓存与版本号的前置约束

当前 GameService.revision **不能直接作为整个 GameSnapshot 的唯一缓存键**。源码中存在多个快照可见状态变化没有同步增加 revision 的路径：

- configure() 可以修改 _engine.react_budget，但没有增加 revision。
- apply_model_settings() 会替换 manager 并写入设置诊断，但没有增加 revision。
- inject() 会修改 manager 内部状态，但没有增加 revision。
- except StopIteration 分支会修改 _done、_running、_status、_last_event_type 并归档，但没有增加 revision。
- Worker heartbeat、等待时长、pending 请求和 manager usage/health 可能独立变化；runtime_diagnostics 还包含按当前时间计算的年龄值。

因此，不能用 revision 命中缓存后直接复用整个旧快照，否则可能返回过期运行状态、诊断或配置。

另一方面，engine/game_engine.py 的活动期日志写入路径具有有利性质：

- public_log 通过 _append_public_item() 追加新事件；整局 load_state() 时才替换列表并重新绑定事件序号。
- reasoning_log 通过 _record_reasoning() 追加；整局 load_state() 时才整体重建。
- 正常游戏流程中，已追加的日志行没有发现原位修改入口。

这为增量日志快照提供了研究基础，但不能据此直接共享当前可变 list/dict。快照消费者仍必须获得不可变数据或独立副本，保持现有快照隔离与视角隐私。

## 6. P2-B 设计建议

按风险和收益排序：

1. **先减少一次页面 rerun 中的重复快照。** 研究将状态同步与 sidebar 配置顺序调整为更少的快照调用。保留真人席位识别、热更新兼容、后台状态刷新和设置即时生效语义。
2. **将稳定游戏状态与动态运行诊断分开。** 为快照可见的引擎状态建立完整版本/代次；manager usage、health、pending 和 worker heartbeat 单独读取或按短时效刷新。
3. **研究 UI 专用轻量快照。** 优先只复制页面当前视角需要的数据；单一真人视角不应为展示而深拷贝其他 11 席的私密推理记录。
4. **研究追加式日志的不可变前缀/分块快照。** 只复制新增日志尾部，并在 load_state() 或列表替换时使缓存失效。完整历史、未读计数、归档和回放仍须保持准确。
5. **暂不实施共享可变引用、无版本保护的缓存或大规模重构。**

建议下一项单独 PR 只做一项可证明的优化：先评估如何在不削弱真人行动安全检查的前提下，将正常活动对局 rerun 的完整快照次数从 3 次降至 1—2 次。之后再决定是否需要增量日志架构。

## 8. P2-B：移除正常 rerun 中间快照（PR #32）

### 代码改动与安全边界

- PR：[移除活动页面刷新中的冗余快照](https://github.com/ClayAllan/SiliconWolfVillage/pull/32)。
- 当前实现：正常活动对局路径从 `422 → 515 → 842` 的三次同步，缩减为 `422 → 842` 两次同步。
- 删除的是 `GameService.configure()` 后、sidebar 内的中间 `sync_game_state()`；保留 rerun 开始时的快照，用于识别真人座位并作为 sidebar 的只读数据视图；保留 sidebar 操作完成后、主工作台渲染前的最新快照。
- `configure()` 会更新调度选项和后续步骤使用的 `react_budget`，但不会修改初始快照中的只读副本。主工作台的第二次同步仍能读取新 `react_budget`；离线回归测试对此有明确断言。
- “应用模型设置”“测试连接”、真人提交行动、终局补归档等条件操作路径仍保留各自的同步调用。
- 未修改 `GameService.snapshot()` 的深拷贝隔离契约、共享锁、后台 worker、引擎状态转换、真人行动完整性保护或权限投影；没有引入共享可变引用和快照缓存。
- sidebar 读取现在统一使用 rerun 开始时的点时快照；主工作台使用 sidebar 操作后的新快照。会有轻微的 sidebar 展示时点差异，但需要改变游戏状态的服务操作仍由 GameService 在锁内重新校验。
